# 허브 화면(샘플)

플랫폼팀이 브라우저에서 허브의 지금 상태를 보는 샘플 화면입니다. 이 PC에서만 열리고, 로그인이 없고, 어디에도 올리지 않습니다. 화면의 모든 값은 그 순간 AWS에서 읽은 것이고(몇 초 동안 다시 씁니다, 아래 "값은 어디서 오나"), 만들어 넣거나 미리 채운 값은 없습니다. 운영용 화면이 아니라 허브가 하는 일을 보여 주는 샘플입니다. Terraform 모듈은 없습니다.

메뉴에는 네 페이지가 있습니다: 홈, 흐름 1의 호스팅 심사, 흐름 2의 전사 정책과 에이전트. 없는 주소는 "이 화면에는 그런 페이지가 없습니다"라는 페이지(404)를 받습니다. 버튼이 있는 페이지는 셸 명령이 부르는 것과 같은 Python 함수를 부르고, 셸 명령은 화면 없이도 그대로 씁니다.

## 실행하는 법

```
make ui                                   # http://127.0.0.1:8300 , Ctrl+C로 멈춥니다
```

- 리전과 접두어는 다른 명령과 같습니다. `make ui`는 `make`의 규칙으로 `.env`도 읽습니다([시작하기의 `.env`](../../docs/getting-started.md#env)). `python -m platform_team.hub_ui`로 직접 실행하면 셸의 `AWS_REGION`, `DEMO_PREFIX`(없으면 `us-west-2`, `hub`)를 쓰고 `.env`는 읽지 않습니다.
- 자격 증명은 실행한 셸의 것입니다. 화면의 모든 읽기와 버튼이 그 자격 증명으로 돕니다. 그 자격 증명이 할 수 있는 것은 화면도 할 수 있습니다.
- `HUB_UI_PORT`: 포트(기본 8300). 주소는 언제나 `127.0.0.1`입니다. 코드에 고정되어 있어 바꾸는 설정이 없습니다.
- `HUB_UI_LANG`: 고르지 않은 페이지의 언어, `ko`(기본) 또는 `en`. 머리줄의 `한 | EN`으로 바꾸면 쿠키 `hub_lang`에 남습니다. 밝게, 어둡게, 자동(OS를 따릅니다)은 쿠키 `hub_theme`에 남습니다.
- `HUB_UI_TZ`: 화면의 시각을 보이는 시간대(기본 `Asia/Seoul`), `MM/DD HH:MM:SS`로 씁니다. 모르는 이름이면 UTC다.
- 허브의 값(SSM `/<prefix>/platform/`)은 그것이 필요한 첫 페이지에서 한 번 읽습니다. 값이 없으면 "배포되어 있지 않다"는 페이지를 보이고, 다음 페이지에서 다시 읽습니다. 그래서 화면을 연 채 `make deploy`를 돌리면 화면이 자동으로 홈으로 바뀝니다(코드가 그렇게 합니다. 해 보지 않았습니다). 반대로 허브를 지우고 다시 올리면 화면은 옛 값을 쥐고 있으므로 화면을 다시 실행합니다.
- 화면은 5초마다 자기를 다시 그립니다. 폼의 칸(입력 칸, 글 칸, 고르는 칸)에 포커스가 있거나 글을 쓰는 칸에 글이 있으면 다시 그리지 않습니다. 다시 그려도 스크롤 위치는 그대로입니다. 링크나 버튼에 있던 포커스는 풀립니다. 이 앱 밖에서 가져오는 스크립트, 스타일, 글꼴은 없습니다.

메뉴의 호스팅 심사 옆 숫자는 승인 대기 중인 에이전트의 수입니다(`panel-counts`와 같은 읽기). 레코드 상태 `PENDING_APPROVAL`은 어느 페이지에서나 `승인 대기`로 적습니다. 심사가 끝난 뒤에도(실패한 심사 옆에서도) 레코드는 결정을 기다리기 때문입니다. 진행 중인 심사 실행은 제 말(`진행 중`)을 씁니다. 각 패널의 읽기는 따로 돕니다. 하나가 실패하면(예를 들어 권한이 없으면) 그 패널에 이유 한 줄이 나오고 나머지 패널은 그대로 보입니다. 읽은 값은 5초 동안 다시 쓰므로 5초 안의 두 페이지는 AWS를 한 번 읽습니다. 실패한 읽기는 다시 쓰지 않습니다.

## 호스팅 심사

`/reviews`는 카탈로그의 에이전트 신청(AGENT 레코드)마다 카드 하나를 보입니다. 카드는 가장 최근 심사가 새로운 것부터 놓입니다. 카드를 누르면 `/reviews/<에이전트>`에서 그 신청 하나를 자세히 봅니다. 심사 하나는 상태 머신 `<prefix>-review`의 실행 하나이고, 화면은 그 실행의 일곱 단계마다 단계를 돌리는 AWS 서비스를 옆에 적습니다(Read, Grant, Entry, TestCall, Approve는 AWS Lambda, Scan과 Deploy는 AWS CodeBuild).

| 패널(`id`) | 보이는 것 | 읽는 곳 |
|---|---|---|
| `panel-applications`(`/reviews`) | 신청마다 이름, 레코드 상태, 팀, 프레임워크, 신청한 도구, 설명, 가장 최근 심사의 상태와 일곱 단계의 띠, 실패했으면 그 단계와 오류 | AWS Agent Registry `ListRegistryRecords`, 레코드마다 `GetRegistryRecord`(신청서는 `descriptors.custom.data`에 있고 목록에는 없습니다), AWS Step Functions `ListExecutions`(새로운 것부터 50개), `DescribeExecution`(입력에 든 레코드 ID), `GetExecutionHistory` |
| `panel-application`(`/reviews/<에이전트>`) | 레코드 상태, 팀, 프레임워크, 신청한 도구, 레코드 ID, 설명 | 위와 같은 읽기 |
| `panel-steps` | 실행의 이름, 상태, 시작 시각, 걸린 시간, 일곱 단계의 띠, 실패한 단계의 오류, 단계마다 하는 일과 돌리는 AWS 서비스와 상태와 걸린 시간의 표, Step Functions 콘솔로 가는 링크 | `GetExecutionHistory` |
| `panel-findings` | Scan에서 실패한 심사만: 스캔 build 로그의 마지막 200줄 가운데 알려진 취약점이 있는 패키지의 줄(pip-audit 표의 이름, 버전, 권고 ID, 고친 버전)과 `submission refused:` 줄, 같은 줄은 처음 나온 자리에 한 번만, 20줄까지 | 실패의 원인(build 기록)에 적힌 로그 그룹과 stream, Amazon CloudWatch Logs `GetLogEvents` |
| `panel-reject` | 반려 사유 칸과 반려 버튼 | 이 앱(아래 "반려") |

단계의 상태는 실행 기록에서 정합니다(`reviews.steps_of`). 단계의 state에 들어간 사건(`TaskStateEntered`)과 나온 사건(`TaskStateExited`) 사이가 그 단계의 시간이고, 나왔으면 통과입니다. 단계의 Catch가 심사를 `Notify`로 보냈으면 그 단계는 실패이고, 오류는 그 단계의 마지막 실패 사건(`TaskFailed` 등)의 error와 cause를 한 줄 300자로 줄인 것입니다. CodeBuild 단계의 cause는 build 기록이라서 build ID, 상태, 실패한 phase와 그 메시지로 줄이고, Lambda 단계의 cause는 함수의 오류 메시지로 줄입니다. Read 뒤에 `Skipped`로 갔으면 나머지 여섯 단계는 건너뜀이고, 아직 닿지 않은 단계는 대기입니다. 진행 중인 단계의 시간은 들어간 때부터 셉니다. 실행이 끝났는데 나오지 않은 단계(중단, 시간 초과)는 실패로 보이고, 그 단계에 실패 사건이 없으면 실행이 끝난 사건의 error와 cause가 오류입니다. 모르는 사건과 이 상태 머신의 단계가 아닌 state는 상태를 바꾸지 않습니다.

읽기 하나가 실패하면 그 읽기가 맡은 곳에만 이유 한 줄이 나옵니다. 실행 목록(`ListExecutions`)을 읽지 못하면 목록 맨 위에 한 줄이 나오고 신청은 그대로 보입니다. 한 실행의 기록(`GetExecutionHistory`)을 읽지 못하면 그 신청의 카드에만 "이 신청의 심사를 읽지 못했습니다"와 이유가 나오고, 다른 카드의 단계는 그대로입니다. 한 실행의 입력(`DescribeExecution`)을 읽지 못하면 그 실행이 어느 신청의 것인지 알 수 없으므로, 아는 가장 최근 심사가 그 실행보다 먼저 시작한(또는 심사가 없는) 신청의 카드가 같은 문장을 보이고, 그보다 나중에 시작한 심사의 카드는 단계를 그대로 보입니다. 한 레코드의 신청서(`GetRegistryRecord`)를 읽지 못하면(목록을 읽은 뒤에 레코드가 지워졌을 때처럼) 그 카드는 이름과 상태와 이유 한 줄만 보이고, 다른 카드는 그대로입니다.

끝난 실행의 입력과 실행 기록, 끝난 지 1분이 지난 심사의 스캔 로그에서 고른 줄은 바뀌지 않으므로 처음 읽은 것을 쥐고 있고, 작업이 끝나도 버리지 않습니다. 화면은 이것을 앱을 다시 실행할 때까지 쥐고 있고, 샘플이라 그 양에 한도를 두지 않았습니다. 진행 중인 실행의 기록과 끝난 지 1분이 안 된 심사의 로그는 5초마다 다시 읽습니다(끝난 바로 뒤에는 build의 마지막 로그 줄이 아직 오는 중일 수 있습니다). 실패한 읽기는 쥐지 않습니다. 스캔의 로그는 Scan에서 실패한 심사의 자세한 페이지에서만 읽습니다. 로그를 읽지 못하면 `panel-findings`에 이유 한 줄이 나오고 단계는 그대로 보입니다.

Step Functions 콘솔 링크는 `/reviews/<에이전트>/console`을 거칩니다. 앱이 그 에이전트의 가장 최근 실행을 찾아 그 리전의 콘솔 주소로 303을 돌려줍니다. 그 주소에는 실행의 ARN(계정 ID가 들어 있습니다)이 들어가므로 페이지 본문에는 ARN을 쓰지 않습니다(아래 "안전 규칙"). 콘솔은 브라우저의 AWS 콘솔 로그인으로 열립니다.

### 반려

반려 버튼은 `reject.sh`가 부르는 함수 `reject_agent.reject`를 작업으로 부릅니다. 사유는 1자에서 255자까지이고(카탈로그의 `statusReason` 한도), 비었거나 길면 작업을 시작하지 않고 그 문장을 빨간 칸에 보입니다. 카탈로그에 그 이름의 AGENT 레코드가 없으면 에이전트 페이지처럼 작업을 시작하지 않고 `/reviews`로 돌아가 "그런 이름의 에이전트는 없습니다"를 보입니다. 카탈로그를 읽지 못하면 작업을 시작하지 않고 AWS에서 값을 읽지 못했다는 문장을 보입니다. 무엇을 바꾸고 지우는지는 그 함수가 셸 명령에서와 똑같이 정합니다. 같은 레코드의 심사가 아직 돌고 있으면 아무것도 바꾸지 않고 멈추고, `APPROVED` 레코드는 받지 않습니다([호스팅 심사의 반려](../hosting_review/README.md)). 작업 칸에는 명령이 출력하는 줄(레코드의 상태, 지운 것, 메모)이 나오고, 함수가 거부하면 그 이유가 나옵니다. 버튼은 레코드가 `PENDING_APPROVAL`, `REJECTED`, `DRAFT`이고 다른 작업이 돌지 않을 때만 보입니다. 심사가 진행 중일 때는 버튼 위에 "심사가 끝난 뒤에 누르라"는 문장이 나옵니다.

### 실행 기록과 로그의 모양을 어디서 가져왔나

실행 기록의 사건 모양(`stateEnteredEventDetails.name`, `taskFailedEventDetails`의 `error`와 `cause` 등)은 Step Functions의 서비스 모델(boto3)에서 가져왔고, 2026-11-23에 올라와 있는 허브에서 이 페이지를 열어(`make e2e-ui`) 진짜 실행과 맞춰 봤습니다. 단계마다 보인 시간은 실행 기록의 들어간 사건과 나온 사건 사이의 시간과 같았습니다(`quality_agent`와 `release_review`의 승인된 심사). Scan에서 실패한 심사에서 AWS는 Scan에 `TaskSubmitted`, `TaskFailed` 다음에 나온 사건(`TaskStateExited`)을 적고 `Notify`로 갔습니다. 코드는 나온 사건이 없다고 가정하고 쓰였지만 나온 사건이 있어도 같은 결과가 되게 썼으므로, 페이지는 Scan을 실패(32초)로 보였습니다. `TaskFailed`의 cause는 build 기록이었습니다(6,419자, 맨 위의 키 `Build`, `SdkHttpMetadata`, `SdkResponseMetadata`. `Build.Logs`에 `GroupName`, `StreamName`, `CloudWatchLogs` 등). build의 마지막 로그 줄은 build가 끝나기 0.1초 전에 CloudWatch Logs에 들어갔고 실행은 build가 끝나고 6.4초 뒤에 멈췄으므로, 실패를 본 뒤 첫 페이지(1초)에 취약점 줄이 나왔습니다. 그 로그의 pip-audit 표(`jinja2 2.11.2  PYSEC-2021-66   2.11.3` 모양의 줄)는 권고 다섯을 줄마다 두 번 출력했고, 페이지는 같은 줄을 한 번만 보입니다. Lambda 단계의 cause(`errorMessage`)는 Lambda 단계가 실패한 심사가 없어 보지 못했습니다. 읽는 곳은 `reviews.py`의 `steps_of`, `scan_log`, `scan_findings` 셋뿐입니다.

## 전사 정책

`/policies`는 두 게이트웨이의 정책, 전사 정책 둘, 커스텀 가드레일을 보이고, 전사 정책 `guard_prompt`의 모드와 커스텀 가드레일을 바꾸는 버튼을 둡니다. 한 모드는 글자로도 보입니다(꺼짐, 기록 모드, 적용 모드). 정책의 `상태`(정책 엔진이 만들고 있는지, 쓸 수 있는지)와 `모드`(적용 모드로 막는지, 기록 모드로 기록만 하는지)는 서로 다른 칸이고 섞어 쓰지 않습니다. 두 표(게이트웨이의 정책과 기록 모드의 집계)의 그 칸 이름은 `모드`입니다(영어 화면은 `Enforcement mode`).

| 패널(`id`) | 보이는 것 | 읽는 곳 |
|---|---|---|
| `panel-company` | `guard_secret`(승인할 때 에이전트마다 걸리고 스위치가 없습니다. 걸려 있는 에이전트의 수)과 `guard_prompt`(모드와 버튼 셋) | SSM `/<prefix>/policies/`(`policy_rollout.deployed`), Policy in Amazon Bedrock AgentCore `ListPolicies` |
| `panel-report` | 최근 60분 동안 `guard_prompt`가 에이전트마다 걸린 요청(`LogOnlyMatches`)과 적용 모드였다면 막았을 요청(`LogOnlyDecisionFlips`) | `policy_rollout.report`(Amazon CloudWatch `GetMetricStatistics`) |
| `panel-guardrail` | 커스텀 가드레일이 붙어 있는지, 붙은 지점, 게이트웨이의 상태, 그리고 해당하는 버튼 하나 | `guardrail_attach.status`(`GetGateway`) |
| `panel-gateway-agent_gw`, `panel-gateway-tool_gw` | 게이트웨이마다 정책의 이름, 종류, 상태, 모드(적용 모드 또는 기록 모드). 도구 허용(`tool_...`)과 공유 읽기 도구 허용(`shared_tool_read`)은 도구 게이트웨이, 나머지 종류는 에이전트 게이트웨이 | `ListPolicies` |
| `panel-other` | 어느 종류의 이름도 아닌 정책(있을 때만) | `ListPolicies` |

버튼은 하나씩 작업을 시작합니다.

| 버튼 | 요청 | 부르는 함수 |
|---|---|---|
| 기록 모드로 걸기, 적용 모드로 올리기, 끄기 | `POST /policies/guard_prompt/mode`, 폼 값 `token`과 `mode`(`log-only`, `active`, `off`) | `policy_rollout.rollout(…, "log-only" 또는 "active")`, `policy_rollout.remove`(`rollout.sh`와 같습니다) |
| 커스텀 가드레일 붙이기, 떼기 | `POST /guardrail/attach`, `POST /guardrail/detach`, 폼 값 `token` | `guardrail_attach.attach`, `guardrail_attach.detach`(`guardrail.sh`와 같습니다) |

지금 모드의 버튼은 눌리지 않습니다. 작업은 명령이 1로 끝나는 경우(에이전트가 실패했거나, 정책 엔진에서 다시 읽은 모드가 다를 때)에 실패로 끝나고 이유는 명령이 출력하는 한 줄과 같습니다. 모르는 전사 정책이나 모드, 모르는 동작은 작업을 시작하지 않고 빨간 칸에 문장을 보입니다. 모드 작업은 함수가 끝난 뒤에 에이전트마다 정책 엔진에서 다시 읽은 모드를 `rollout.sh`가 출력하는 줄 그대로 한 줄씩 작업 칸에 적습니다(`policy_rollout.say_read`: `<에이전트>: reads LOG_ONLY`, `<에이전트>: reads no policy`, 정한 것과 다른 모드면 `<에이전트>: reads <모드>, asked for <정한 모드>`).

## 에이전트

`/agents`는 호스팅된 에이전트의 사용량, 도구 호출 경보, 도구별 호출 수를 보이고, 멈춤과 재개 버튼을 둡니다.

| 패널(`id`) | 보이는 것 | 읽는 곳 |
|---|---|---|
| `panel-alarm` | 경보 `<prefix>-tool-calls`의 상태(`OK`, `ALARM`, `INSUFFICIENT_DATA`), 임계값, 감시하는 도구, 최근 15분의 1분 합계 막대와 임계값 선. 임계값을 넘은 막대는 다른 색, 굵은 테두리, `▲` 표시로 보입니다 | Amazon CloudWatch `DescribeAlarms`, 그 경보의 지표를 경보의 차원 그대로 `GetMetricData` |
| `panel-agents` | 에이전트마다 팀, 프레임워크, 호스팅 방식(`Runtime` 또는 `harness`), 카탈로그 상태, 멈춤 상태, 최근 60분의 호출, 세션, 오류, vCPU-시간, GB-시간, 멈춤이나 재개 버튼 | `usage_report.hosted_agents`와 `usage_report.usage`(`GetMetricData`), `stop_agent.stopped`(`ListPolicies`), `ListGatewayTargets`, 카탈로그 |
| `panel-tools` | 도구마다 최근 60분의 호출 수(모든 호출자의 합) | `usage_report.tool_calls` |

harness 에이전트는 에이전트 게이트웨이에 진입이 없어 멈추는 버튼 대신 그 이유를 보이고, 그 멈춤 상태는 읽지 않으므로 칸에 `—`를 보입니다. 한 에이전트의 멈춤 상태나 카탈로그 레코드를 읽지 못하면 그 줄에만 이유가 나오고(멈춤 상태를 모르면 그 줄에는 버튼이 없습니다), 사용량을 읽지 못하면 표 위에 한 줄이 나오고 줄은 사용량 없이 보입니다.

| 버튼 | 요청 | 부르는 함수 |
|---|---|---|
| 멈추기 | `POST /agents/<에이전트>/stop`, 폼 값 `token` | `stop_agent.stop`(`stop.sh`와 같습니다) |
| 재개 | `POST /agents/<에이전트>/resume`, 폼 값 `token` | `stop_agent.resume`(`resume.sh`와 같습니다) |

멈추기는 끝내지 못한 세션이 있으면 명령처럼 실패로 끝납니다. 에이전트 이름이 신청서의 이름 규칙에 맞지 않거나 호스팅된 에이전트가 아니면 작업을 시작하지 않고 빨간 칸에 문장을 보입니다. 누른 때 호스팅된 에이전트의 목록을 읽지 못해도 작업을 시작하지 않고 빨간 칸에 그 문장(AWS에서 값을 읽지 못했습니다)을 보입니다.

두 페이지는 2026-11-23에 가짜 AWS 값으로 확인했고, 같은 날 올라와 있는 허브에서 `make e2e-ui`가 버튼을 눌러 확인했습니다(아래 "테스트와 확인").

## 작업(버튼)

버튼은 셸 명령과 같은 함수를 이 앱 안의 작업(thread)으로 돌립니다. 버튼을 누르면 앱은 언제나 페이지로 돌려보내고(303), 그 페이지가 결과의 문장을 보입니다. 받은 것은 초록 칸, 받지 않은 것(빠지거나 맞지 않는 값, 모르는 이름)은 빨간 칸입니다. 작업은 한 번에 하나입니다. 작업이 도는 동안 다른 버튼을 누르면 받지 않고, 누른 페이지로 돌아가 "다른 작업이 진행 중"이라는 문장을 보입니다. 작업이 도는 동안 페이지는 2초마다 그 작업이 출력한 줄을 다시 그리고, 작업이 끝나면 한 번 새로 읽습니다. 앱을 다시 실행해 그 작업이 없어졌을 때도 한 번 새로 읽습니다. 작업이 끝나면 다시 쓰던 값을 버리므로 그 뒤의 페이지는 AWS를 새로 읽습니다. 작업 칸의 줄은 페이지의 언어와 상관없이 영어입니다(모드 작업이 다시 읽은 모드의 줄은 `rollout.sh`가 출력하는 줄 그대로입니다). 실패한 작업은 이유를 한 줄로 보입니다(계정 ID는 `<ACCOUNT>`). 작업은 메모리에만 있어서 앱을 멈추면 사라집니다. 작업이 도는 중에 앱을 멈추면 그 함수도 중간에 멈춥니다(작업의 thread는 앱과 함께 끝납니다. 코드가 그렇게 합니다. 해 보지 않았습니다). 버튼이 있는 페이지는 호스팅 심사(반려), 전사 정책(모드, 가드레일), 에이전트(멈춤, 재개)입니다. 작업이 도는 동안에는 그 버튼들이 눌리지 않습니다.

## 안전 규칙

로그인이 없는 화면이 AWS를 바꿀 수 있으므로, 앱은 이것들을 모든 요청에 지킵니다(`safety.py`). 거부된 요청은 경로에 닿지 않습니다. AWS를 부르지 않고 작업을 시작하지 않습니다.

- 이 PC의 주소로만 엽니다. 앱은 `127.0.0.1`에서만 듣습니다. 요청의 `Host`가 `127.0.0.1:<포트>`나 `localhost:<포트>`가 아니면 403입니다. 다른 사이트가 자기 이름을 `127.0.0.1`로 돌려 놓고(DNS rebinding) 브라우저로 부르면 그 이름이 `Host`에 실리므로 거부됩니다.
- 바꾸는 요청(GET과 HEAD가 아닌 것)은 이 화면의 페이지에서 온 것만 받습니다. `Origin`이 `http://127.0.0.1:<포트>`나 `http://localhost:<포트>`이어야 하고(`Origin`이 없으면 거부), HTML 폼의 숨은 칸 `token`에 페이지 토큰이 있어야 합니다. 토큰은 앱을 실행할 때마다 새로 만들고, 이 화면의 페이지에만 들어 있습니다(상수 시간으로 비교합니다). 앱을 다시 실행한 뒤 예전 탭에서 누르면 403이고, 페이지를 다시 열면 됩니다.
- 다른 사이트가 이 화면을 자기 페이지 안의 틀(frame)에 넣지 못합니다(`X-Frame-Options: DENY`, `Content-Security-Policy`의 `frame-ancestors 'none'`). 틀에 넣은 화면 위에서 누르게 하는 속임수를 막습니다. 같은 정책이 페이지의 스크립트로는 이 앱이 쓴 두 스크립트만 돌게 합니다. 둘에는 앱을 실행할 때마다 새로 만드는 nonce가 붙어 있어서, 값에 섞여 들어온 마크업이 이스케이프를 지나더라도 스크립트로는 돌지 않습니다. 이 앱 밖의 스크립트, 스타일, 그림도 가져오지 못하게 하고, 폼은 이 앱의 주소로만 보내게 합니다(`form-action 'self'`).
- 계정 ID는 앱이 돌려주는 본문에 나오지 않습니다. 앱이 보내는 모든 HTML과 JSON 본문을 `aws_helpers.mask`에 통과시켜 12자리 계정 ID를 `<ACCOUNT>`로 바꿉니다. 허브의 값을 읽기 전(계정을 아직 모를 때)에는 12자리 숫자를 모두 바꿉니다. 본문이 아닌 곳에 계정 ID가 나가는 것은 하나뿐입니다. Step Functions 콘솔로 가는 303의 주소(`Location`)에는 실행의 ARN이 들어 있고, 그 ARN에 계정 ID가 있습니다(위의 "호스팅 심사").
- 개발자나 에이전트가 정한 글(레코드의 설명, 팀, 프레임워크, 시험 호출의 답, 오류)은 템플릿 엔진이 이스케이프합니다. 템플릿의 파일 이름과 상관없이 모든 템플릿이 이스케이프합니다. 이스케이프하지 않는 것은 이 리포가 쓴 마크업(메뉴의 아이콘)뿐입니다.

이 규칙이 막지 못하는 것:

- 다른 사이트의 페이지가 브라우저에게 이 화면의 페이지를 GET하게 하는 것(링크, 그림 주소). `Host`는 `127.0.0.1:<포트>`라서 받으므로, 그 페이지의 AWS 읽기가 실행한 셸의 자격 증명으로 돕니다. 바꾸는 요청은 아니고, 그 사이트는 답을 읽지 못합니다(브라우저는 다른 출처의 답을 그 사이트의 스크립트에 넘기지 않습니다).
- 이 PC에서 도는 프로그램과 이 PC의 다른 사용자. 그들은 `127.0.0.1:<포트>`를 부를 수 있고, 페이지(GET은 토큰이 필요 없습니다)에서 토큰을 읽어 버튼을 누를 수 있습니다. 여럿이 쓰는 PC에서는 실행하지 않습니다.
- 브라우저 확장 프로그램처럼 이 화면의 페이지 안에서 도는 코드.
- 앱 앞에 프록시를 두거나 포트를 밖으로 여는 것. 앱은 그런 쓰임을 생각하지 않았습니다.
- 자격 증명의 범위. 화면은 실행한 셸의 자격 증명이 허락하는 만큼 할 수 있습니다.
- 통신은 HTTP다. 이 PC 안의 통신(loopback)이라 암호화하지 않습니다.

## 테스트와 확인

동작은 단위 테스트가 정합니다(`tests/test_hub_ui_app.py`, `tests/test_hub_ui_jobs.py`, `tests/test_hub_ui_home.py`, `tests/test_hub_ui_reviews.py`, `tests/test_hub_ui_policies.py`, `tests/test_hub_ui_agents.py`). 테스트는 `tests/fakes.py`의 가짜 AWS 클라이언트로 돌고 AWS를 부르지 않습니다. 2026-11-23에 허브가 올라와 있지 않은 계정(`us-west-2`, 접두어 `hub`)에서 `python -m platform_team.hub_ui`로 실행해 봤습니다. 첫 페이지가 200으로 "이 계정과 리전에 허브가 배포되어 있지 않습니다"와 읽은 곳(`/hub/platform/`)을 보였고, `Host: evil.example:8300`인 요청은 403이었습니다.

`make e2e-ui`(`e2e_checks/e2e_hub_ui.py`)는 올라와 있는 허브에서 화면을 확인합니다. `make e2e-ops`가 끝난 허브(에이전트 넷이 호스팅되고 `APPROVED`, `guard_prompt` 꺼짐, 커스텀 가드레일 떨어짐, 멈춘 에이전트 없음, 도는 심사 없음)에서만 시작하고, 아니면 0번 줄에 무엇이 다른지 출력하고 멈춥니다. 화면을 이 PC의 빈 포트에서 자식 프로세스(`python -m platform_team.hub_ui`)로 실행하고, 페이지를 읽고 브라우저처럼 버튼을 누릅니다(페이지에서 읽은 토큰과 화면의 `Origin`). 끝나면 실패했을 때도 자식을 멈춥니다. 페이지에서 읽은 값은 스크립트가 boto3로 읽은 값과 맞춰 봅니다. 확인 여덟을 한 줄씩 출력하고(`[PASS]`, `[FAIL]`, 관찰은 `[INFO]`), 끝 줄은 `== N checks passed, M failed, K observations (…s)`입니다.

1. 모든 페이지가 200이고 `샘플 화면`이 있고 계정 ID가 없습니다. 페이지마다 캐시가 지난 첫 읽기와 바로 뒤의 둘째 읽기에 걸린 시간을 출력합니다.
2. 홈의 수와 경보가 카탈로그와 CloudWatch가 주는 것과 같고, 플랫폼 구성의 여섯 줄이 저마다 상태를 보입니다.
3. 호스팅 심사 페이지에서 `quality_agent`와 `release_review`가 `APPROVED`이고, 가장 최근 심사의 일곱 단계가 모두 통과이며, 단계마다의 시간이 Step Functions의 실행 기록과 같습니다(1초 안).
4. `quality_agent`의 취약한 변형을 제출하면 페이지가 Scan에서의 실패와 취약점 줄을 하나 이상 보입니다. 사유와 함께 반려를 누르면 레코드의 상태가 작업이 출력한 상태와 같습니다. 고친 버전을 다시 제출하면 페이지가 `APPROVED`를 보입니다.
5. 기록 모드로 걸기 뒤에 페이지와 정책 엔진이 호스팅된 Runtime 에이전트마다 `LOG_ONLY`를 읽고, 숨은 지시 하나를 보내면 페이지의 집계가 그것을 셉니다. 적용 모드로 올리기 뒤에는 `ACTIVE`이고, 끄기 뒤에는 정책이 없습니다.
6. 커스텀 가드레일 붙이기 뒤에 페이지와 `guardrail_attach.status`가 붙어 있다고 읽고, 코드명이 줄바꿈 바로 뒤에 오는 요청이 interceptor에서 403입니다. 떼기 뒤에는 둘 다 떨어져 있다고 읽습니다.
7. `quality_agent` 멈추기 뒤에 페이지가 멈춤을 보이고, 에이전트 게이트웨이로 부르면 403이고 `release_review`는 200입니다. 재개 뒤에 페이지가 동작 중을 보이고 부르면 200입니다.
8. 작업이 도는 동안 버튼을 다시 누르면 받지 않습니다(303과 `err=busy`, 그리고 페이지의 문장).

바꾼 것은 확인마다 되돌리므로(취약한 버전은 반려하고 고친 버전을 다시 승인, `guard_prompt`는 꺼짐, 가드레일은 떨어짐, `quality_agent`는 재개) 같은 허브에서 다시 돌릴 수 있습니다. 확인이 중간에 멈추면, 끝에서 남은 것 가운데 전사 정책 `guard_prompt`, 커스텀 가드레일, 멈춘 에이전트를 리포의 명령(`rollout.sh guard_prompt off`, `guardrail.sh detach`, `resume.sh`)으로 되돌립니다. `quality_agent`의 레코드는 되돌리지 않습니다. 4번이 중간에 멈춰 그 레코드가 `APPROVED`가 아니면, 끝에 그것을 되돌리는 명령(`dev_team/agent_template/publish.sh dev_team/quality_agent`, 그다음 호스팅 심사 페이지나 `make e2e-ui`의 0번 줄이 `APPROVED`로 읽을 때까지 기다립니다)을 한 줄로 출력하고, 다음 실행의 0번 줄도 같은 명령을 말합니다. `E2E_UI_HOLD=<초>`를 주면 네 페이지(실패한 심사, 집계가 요청을 센 기록 모드, 붙은 가드레일, 멈춘 `quality_agent`)를 그만큼 그대로 둔 뒤에 다음 버튼을 누릅니다. 화면을 보거나 녹화하기 위한 것입니다. 기록은 `e2e_checks/last-run-ui.log`에 남습니다.
